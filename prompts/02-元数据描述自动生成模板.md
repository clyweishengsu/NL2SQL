# 模板 02：元数据描述自动生成模板（AI 一键生成草稿）

> 文件：`prompts/02-元数据描述自动生成模板.md`
> 版本：v1.1.0 ｜ 产出人：文达意 ｜ 日期：2026-09
> 对应功能：**F-23 AI 一键生成描述草稿**（配合 表解释、字段描述、术语建议）
---

## 0. 核心结论（先看这里）

| # | 结论 |
|---|---|
| 1 | 本模板产出的**永远是"草稿"**，不是"结论"：所有内容必须经人工校对后才发布（验收 F-23「供人工校对」、F-05/F-06「AI 生成草稿→人工校对」）。 |
| 2 | **禁止编造业务口径**：模型只能从「DDL + 样本数据 + 已有人工描述」中**归纳**，不得凭常识发明含义；不确定的字段一律降低 `confidence` 并标 `needs_human_review=true`。 |
| 3 | 输出结构化 JSON：表级（业务名/解释/用途）+ 字段级（业务名/描述/枚举值/同义词建议）+ 草稿置信度标记。 |
| 4 | **已有手填描述默认不覆盖**（验收 F-23 边界）：模板只输出"建议"，由前端做差异确认。 |
| 5 | 样本数据必须**脱敏 + 剔除敏感字段**后再进入本模板（N-14/N-16）。 |
| 6 | 本模板的价值锚点：本项目底座里 `amt_a`/`amt_b`/`flag`/`rst` 等**原生注释无意义**的列，正是"AI 必须说『待确认』而不是瞎猜"的典型——示例见 §4。 |

## 1. 模板全文（可直接复制粘贴进代码）

```text
# ============ 系统指令（固定） ============
你是系统的元数据助手。你的任务是：依据给定的数据库表结构（DDL）、少量样本数据、以及已有的人工描述，为这张表生成「业务解释草稿」与「字段描述草稿」，供数据管理员人工校对后使用。

## 你只能做"归纳"，不能做"编造"（最重要）
1. 你输出的每一条描述，都必须能追溯到输入中的证据：DDL 字段名/类型/主外键、样本数据取值、已在输入中给出的人工描述。
2. 严禁凭个人常识发明业务口径。例如：不得因为字段名叫 amount 就断言"这是含税金额"；不得因为字段叫 flag 就断言它表示"是否有效"；不得因为列名叫 amt_a 就猜它是什么。若无法从证据判断，就把该字段描述写为"（待确认）<从字段名与类型可推断的最保守描述>"，并令 needs_human_review = true。
3. 涉及"含税/不含税""是否软删除""统计口径""单位（元/万元）""枚举数字含义"这类关键口径，除非输入中已有明确的人工描述或原生 COMMENT 给出了含义，否则必须在 description 中标注 [待人工确认]，且不得给出确定性结论。
4. 【特别注意】若原生 COMMENT 无含义（例如 COMMENT 内容就是字段名本身，如 `amt_a` 的注释就是 "amt_a"），必须视为"无注释"，不得据此推断任何业务含义，description 必须标 [待人工确认] 且 needs_human_review = true、confidence ≤ 0.4。
5. 枚举值只允许从样本数据的实际取值分布中归纳；样本未覆盖的取值，不要臆测，标注 [取值可能不全]。

## 输出约束
- 只输出一个 JSON 对象，不要输出 JSON 以外的任何文字或 Markdown 代码块。
- 所有自然语言字段使用简体中文，简洁、面向业务人员、避免技术黑话。
- 不得输出 SQL 语句；不得建议"删除/新增字段"等结构变更。
- 若提供了"已有描述"，你的任务是**建议优化**，不得直接判定其错误；在 conflicts 中列出你与已有描述的分歧点。

# ============ 任务输入 ============
## 行业背景
{{industry_context}}

## 目标对象
{{object_type}}   # table / column / all

## 表结构（DDL）
{{ddl}}

## 样本数据（已脱敏，最多 {{sample_row_limit}} 行）
{{sample_rows}}

## 已有的人工描述（可能为空）
{{existing_docs}}

# ============ 输出要求 ============
输出 JSON，结构如下：

{
  "table": {
    "table_name": "物理表名",
    "business_name": "表业务名建议，例如：投标记录表",
    "table_doc": "表解释草稿：这张表记录什么、一条记录代表什么粒度、典型使用场景",
    "purpose": "用途说明草稿，可选",
    "row_scale_hint": "从样本或常识估计的行数量级，无法判断填 '未知'",
    "confidence": 0.0
  },
  "columns": [
    {
      "column_name": "物理字段名",
      "business_name": "字段业务名建议",
      "description": "字段业务描述草稿",
      "enum_values": {"1": "含义", "2": "含义"},
      "synonyms": ["业务口语同义词"],
      "is_sensitive_suggestion": false,
      "confidence": 0.0,
      "needs_human_review": false,
      "evidence": "本字段描述的依据，例如：字段名 rst + 样本取值 {2,3,4}"
    }
  ],
  "term_suggestions": [
    {
      "term": "建议的业务术语名",
      "synonyms": ["同义词"],
      "definition": "口径定义草稿",
      "related_columns": ["表名.字段名"],
      "confidence": 0.0
    }
  ],
  "conflicts": [
    {
      "target": "table 或 字段名",
      "existing": "已有描述内容",
      "suggested": "你的建议",
      "reason": "分歧原因"
    }
  ]
}

## 判断规则
- confidence 取值 0~1：
  * ≥0.8：证据充分（字段名含义清晰 + 样本数据可印证）
  * 0.5~0.8：可较合理推断，但仍需确认
  * <0.5：证据不足，仅给出最保守猜测
- needs_human_review = true 的情形（必须置 true）：
  * confidence < 0.8；
  * 原生 COMMENT 无含义（注释等于字段名）或字段名是缩写/拼音/无意义列名（如 flag、type、val、num、amt_a、bz 等）；
  * 字段涉及金额/税率/时间/状态/单位等关键口径；
  * 样本数据缺失或空表；
  * 枚举值来源于样本但可能不全。
- enum_values、synonyms 无内容时输出空对象 {} 或空数组 []，不要省略字段、不要编造同义词。
- is_sensitive_suggestion：字段名/样本值疑似身份证、手机号、银行账号、家庭住址、精确人名等，置 true。
```

## 2. 变量说明表

| 变量名 | 类型 | 来源 | 必填 | 示例值 | 缺失降级 |
|---|---|---|---|---|---|
| `{{industry_context}}` | string | 产品配置 | 否 | `建筑/招投标行业` | 缺失 → 用通用描述，confidence 上限 0.6 |
| `{{object_type}}` | enum | 配置台 | 是 | `all` | 缺失 → 默认 `all` |
| `{{ddl}}` | string | 反向解析/DDL 上传 | 是 | `CREATE TABLE t_bid_record (...)` | 缺失 → 中止（无法生成） |
| `{{sample_rows}}` | string | 数据库抽样（**脱敏+去敏感字段**） | 否 | `[{"bid_id":"B0001","rst":"2","bid_price":"88500000.00"}]` | 缺失 → 全靠字段名推断，confidence 上限 0.6，needs_human_review 全置 true |
| `{{sample_row_limit}}` | int | 配置台 | 否 | `5` | 缺失 → 默认 5 |
| `{{existing_docs}}` | string | 已有人工描述 | 否 | `bid_price 已有描述：投标报价(含税)` | 缺失 → 无 conflicts 分区 |

> **安全前置（dev 必做）**：进入本模板前，样本数据须 ①剔除 `is_sensitive=true` 字段（如 `t_manager.tel`）；②手机号/身份证/账号做掩码；③行数 ≤ `sample_row_limit`。

## 3. 使用说明（何时调用 / 调用参数）

| 项 | 说明 |
|---|---|
| 调用时机 | 配置台 P-03 点击「AI 生成草稿」（F-23）；可作用于单表全部字段、单表指定字段、或单字段 |
| 调用次数 | 每次点击 1 次；批量按表循环（前端控制并发） |
| 模型参数 | `temperature=0.2`（略高于生成 SQL，允许归纳语言更自然，但不允许发散）、`max_tokens=2048` |
| 结果处理 | ①**默认不覆盖**已有手填内容，展示为"建议"由用户逐条采纳（验收 F-23 边界）；②`needs_human_review=true` 的字段高亮提示；③`conflicts` 单独区域展示分歧 |
| 发布校验 | 采纳后的内容与手填内容一致地走 F-08 发布校验（表解释必填 + ≥80% 字段有描述，见待确认项） |

## 5. 已知边界与失败模式

| 失败模式 | 现象 | 缓解 |
|---|---|---|
| **把无含义注释当含义** | 因 `amt_a` 的注释是 `amt_a` 就以为"有注释"，甚至猜成"评标价" | 模板「特别注意」条款（注释等于字段名=无注释）+ 强制 `[待人工确认]` |
| 编造业务口径 | 把 `flag` 说成"是否有效"、把 `amt_a` 说成"评估价" | 模板硬约束 + 关键口径强制待确认 + `needs_human_review` |
| 缩写字段臆测 | `rst`/`amt_b` 被强行赋予含义 | confidence <0.5 且必标待确认 |
| 枚举不全 | 样本只出现 2、3、4，却输出 1~4 全部含义 | 模板要求「标注 [取值可能不全]」，且枚举只来自样本 |
| 样本泄露敏感数据 | 手机号/身份证进入 Prompt（如 `t_manager.tel`） | dev 前置脱敏 + 剔除敏感字段（N-14/N-16） |
| 覆盖人工描述 | 直接把手填内容替换 | 「默认不覆盖」由前端差异确认实现；模板只出建议 |
| JSON 输出不稳 | 小模型包裹 Markdown | 解析兜底同 README §5.2；失败重试 1 次 |

## 6. 

| # | 项 | 建议默认 |
|---|---|---|
| 1 | 是否允许对本表**批量**生成（整库一键） | 建议 MVP 单表，V1 批量 |
| 2 | 样本数据行数上限 | 5 行（`sample_row_limit`） |
