## 0. 核心结论（先看这里）

| # | 结论 |
|---|---|
| 1 | 体系共 **6 个模板**：`01` 主 NL2SQL、`02` 元数据草稿生成、`03` 自审与自纠错、`04` SQL 反向解释、`05` 表召回与 Schema Linking、`06` 黄金 SQL 示例库组织规范。 |
| 2 | **一次完整问答 = 1~2 次 LLM 调用**（表召回走向量、不额外调 LLM；主生成 1 次 + 最多 2 次自纠错重试）。 |
| 3 | **主模板（01）统一输出严格 JSON**（`sql`/`rationale`/`used_tables`/`used_terms`/`confidence`/`need_clarification`/`clarification_question`/`assumptions`），由程序解析后再做 SELECT-only 校验。 |
| 4 | **准确性优先**：证据不足时强制返回 `need_clarification`，**禁止猜测**；歧义相似列名（本项目真实陷阱：`bid_price`/`amt_a`/`amt_b` 三价格列、`region_cd`/`reg_txt`/`area_txt` 三区域口径）是头号幻觉来源，专门设澄清规则。 |
| 5 | **上下文长度敏感**（MotherDuck 已证小模型长上下文掉点）：元数据分区严格预算 + 表召回，不做全量注入。 |
| 6 | **只读硬约束双保险**：Prompt 层（模板内硬约束）+ 程序层（AST 白名单校验），Prompt 不是唯一防线。 |
| 7 | **全项目一套 Schema**：所有模板示例与 Few-shot 统一使用 `tests/golden/00-示例Schema-招投标业务.md`（7 表，与 Demo / Golden SQL 共用），避免 few-shot 与真实元数据命名冲突。 |

## 2. 变量字典

> 约定：变量语法统一为 `{{变量名}}`；`string` 类型默认空串；`list/json` 类型默认 `[]`/`{}`。
> **安全约定**：所有来自用户输入的变量（`user_question`、`history_summary`）在与系统指令拼接时**必须包裹在定界符内**（见模板 01 §注入防护），不得与指令区直接拼接。

### 2.1 全局变量（多模板共用）

| 变量名 | 类型 | 来源 | 必填 | 示例值 | 缺失时降级行为 |
|---|---|---|---|---|---|
| `{{dialect}}` | string | 数据源 `db_type` | 是 | `mysql` / `postgresql` | **不可缺失**：缺失则中止生成，提示配置异常 |
| `{{current_date}}` | date | 系统时钟 | 是 | `2026-09-15` | 由程序注入，不可缺；缺失时模板要求模型不做时间推断并触发澄清（若问题含相对时间） |
| `{{schema_context}}` | string（已渲染文本） | 元数据服务（表召回结果渲染） | 是 | 见模板 01 §4 | 为空 → 返回 `need_clarification`，问「未检索到可用表，请确认数据域/表是否已配置」 |
| `{{terms_context}}` | string | 业务术语库（F-18） | 否 | 见模板 01 §4.4 | 空串 → 模板自动省略该分区，模型不得自行发明术语口径 |
| `{{few_shot_examples}}` | string（已渲染 Q/SQL 对） | 黄金示例库（F-19） | 否 | 见模板 01 §5 | 空串 → 走零样本（Few-shot K=0），模板标注「无参考示例」 |
| `{{user_question}}` | string | 用户输入（≤1000 字，见 F-09） | 是 | `上个季度各区域中标金额前10` | **不可缺失**；空 → 不调用 LLM，直接提示「请输入问题」 |
| `{{history_summary}}` | string | 多轮对话摘要（F-09） | 否 | `上一轮问了：各区域投标数量` | 空串 → 单轮模式 |
| `{{permission_scope}}` | json（表/字段白名单） | 权限服务（F-15） | 是 | `{"tables":["t_bid_record","t_section"],"denied_columns":["t_manager.tel"]}` | **不可缺失**：缺失则拒绝生成（安全优先）；模板把它作为只读白名单二次声明 |
| `{{token_budget}}` | int | 生成服务（按模型窗口计算） | 是 | `8192` | 缺失 → 用默认 8192 并告警 |
| `{{model_profile}}` | enum | 模型适配层（F-10） | 是 | `qwen` / `deepseek` / `cloud-api` | 缺失 → 默认 `qwen` 档 |

## 3. Token 预算与裁剪策略（可执行规则）

### 3.1 预算计算（程序侧，非 LLM）

```
# 1) 有效预算
B_eff = ctx_window - max_output_tokens - SAFETY_MARGIN
#   ctx_window：模型上下文（Qwen2.5-32B=32K / DeepSeek-V3=64K / 云 API 按实际）
#   max_output_tokens：建议 1024（JSON 契约输出足够）
#   SAFETY_MARGIN：512（tokenizer 偏差、模板定界符、系统开销）

# 2) 分区预算
B_sys     = 0.10 * B_eff   # 系统指令 + 输出要求（固定，不裁剪）
B_meta    = 0.55 * B_eff   # 元数据分区
B_fewshot = 0.25 * B_eff   # 示例分区
B_reserve = 0.10 * B_eff   # 历史摘要 + 安全兜底

# 3) 估算函数（中英混合启发式，误差 ±15%）
est(text) = ceil(0.6 * n_cjk + 0.30 * n_latin_word + 0.10 * n_punct)
#   或工程简化：est ≈ len(chars)/2（中文为主场景）；DDL/英文标识符 est ≈ len(chars)/3.5
```

### 3.2 裁剪优先级（保序：先保前，后裁剪）

> PRD §8.2 原文「完整表 > 关键字段 > 相似字段 > 示例条数」= **保护优先级**，即裁剪时**从右往左**动刀。

| 级别 | 保护对象 | 触发条件 | 动作 | 预期回收 |
|---|---|---|---|---|
| L0 | — | 全部在上限内 | 不裁剪 | — |
| L1 | 完整表结构（DDL+表解释） | `est(meta) > B_meta` | **先减示例条数**：K 由 5→3→1→0 | 每减 1 条约 200~400 token |
| L2 | 关键字段描述 | L1 不够 | **截断「相似字段」描述**：低相似度字段仅保留 `名+类型`，丢弃描述 | 每字段约 30~80 token |
| L3 | 相似字段描述 | L2 不够 | **截断「关键字段」描述**：保留命中字段名+枚举值，描述压缩至 ≤20 字 | 每字段约 50~150 token |
| L4 | 表结构 | L3 不够 | 非命中表**降级为「表名+表解释+主键/外键」**，丢弃其余字段 DDL | 每表约 200~600 token |
| L5 | 兜底 | L4 仍超 | 减少召回表数（N-1 递减，最低 3 张），并在调试页标红；若 <3 张仍超 → 拒绝生成并提示「元数据过大，请精简配置」 | — |

**关键字段 vs 相似字段判定**：向量相似度分 ≥ 阈值 T_key（默认 0.62）或出现在用户问题字面/术语映射中 → **关键字段**；否则 → **相似字段**。

**裁剪后必须校验**：若被裁掉的表/字段出现在 `used_tables`/`used_terms` 声明里 → 视为「依据不足」，要求模型重判或触发澄清。

### 3.3 预算占用埋点（供 P-08 调试页展示）

程序须输出分区占用表，字段固定：

| 分区 | est_tokens | 预算 | 占用率 | 是否裁剪 | 裁剪动作 |
|---|---|---|---|---|---|
| system | — | `B_sys` | — | 否 | — |
| metadata | — | `B_meta` | — | 是/否 | L1~L5 |
| few_shot | — | `B_fewshot` | — | 是/否 | K 值 |
| reserve | — | `B_reserve` | — | — | — |

## 4. 调用顺序与时序（一次完整问答）

| 步 | 动作 | 模板 | LLM 调用 | 失败分支 |
|---|---|---|---|---|
| 1 | 解析问题、加载数据域、权限过滤 | — | 否 | 无权限 → 拒绝并提示 |
| 2 | 表数量判定 | — | 否 | ≤200 → 全量注入；>200 → 步骤 3 |
| 3 | 表召回（向量 Top-N → LLM 复排） | **05** | **是（1 次，可缓存）** | 召回为空 → 提示「未找到相关数据表」 |
| 4 | 组装上下文、预算裁剪 | — | 否 | 超预算 → §3.2 逐级降级 |
| 5 | 主生成 | **01** | **是（1 次）** | JSON 解析失败 → 见 §5.5 兜底 |
| 6 | 程序层 SELECT-only 校验（F-12） | — | 否 | 拦截 → 重生成（并入重试计数，≤2） |
| 7 | 事前自审（可选） | **03a** | 是（1 次） | `needs_fix` → `fixed_sql` **必须重跑步骤 6** |
| 8 | 执行（只读） | — | 否 | 报错 → 步骤 9 |
| 9 | 事后纠错 | **03b** | 是（≤2 次） | 达上限 → 提示人工介入 |
| 10 | 结果展示 + 反向解释（按需） | **04** | 是（按需） | 解释失败不影响主流程 |
| 11 | 采纳/纠错 → 沉淀 | **06** | 否 | — |

**总 LLM 调用上限**：主生成 1 + 表召回 1 + 自纠错 ≤2 = **≤4 次**；其中与用户等待强相关的仅主生成 1 次（P95 ≤ 8s，N-07）。

## 5. 输出契约与解析兜底（全局）

### 5.1 主生成 JSON 契约（模板 01）

| 字段 | 类型 | 必填 | 取值/说明 |
|---|---|---|---|
| `sql` | string \| null | 是 | 单条 SELECT；`need_clarification=true` 时为 null |
| `rationale` | string | 是 | 生成依据：引用命中的表/字段/术语/示例，中文 ≤200 字 |
| `used_tables` | string[] | 是 | 用到的物理表名（须来自 `schema_context`，禁止编造） |
| `used_terms` | string[] | 否 | 命中的业务术语名 |
| `confidence` | number | 是 | 0~1，模型自评置信度 |
| `need_clarification` | bool | 是 | 证据不足时为 true |
| `clarification_question` | string \| null | 是 | `need_clarification=true` 时必填，中文提问 |
| `assumptions` | string[] | 否 | 显式假设（如「默认排除废标记录」） |

### 5.2 解析与兜底策略（程序侧）

| 情形 | 处理 |
|---|---|
| 整体非 JSON | 尝试抽取 ```` ```json ... ``` ```` 代码块；再失败 → 重试 1 次（提高约束强度）→ 仍失败 → 拦截，提示「生成格式异常，请重试」 |
| JSON 合法但缺字段 | 用默认值补：`used_tables=[]`、`confidence=0.3`、`assumptions=[]`；缺 `sql` 且 `need_clarification≠true` → 按失败处理 |
| `sql` 非单条 SELECT | 交 F-12 拦截，进入重生成流程 |
| `used_tables` 含未注入表 | 视为幻觉 → 降 `confidence` 至 ≤0.3，触发重新生成（重试计数 +1） |
| `confidence < 0.5` 且 `need_clarification=false` | 前端提示「置信度较低，建议人工复核」 |

## 6. 模型适配说明

| 维度 | Qwen（本地，如 Qwen2.5-32B/72B） | DeepSeek（V3/R1 本地或私有） | 通用云 API |
|---|---|---|---|
| 系统提示词支持度 | 支持 `system` role；建议把硬约束同时放进 system 与 user 首段（双保险） | 支持 `system` role；对长 system 更宽容 | 视厂商，统一放 system |
| JSON 输出稳定度 | 中（**必须**要求「仅输出 JSON、无 Markdown 包裹」+ 给一例） | 中高 | 高（部分支持 response_format=json） |
| 长上下文表现 | **敏感**（32B 在长上下文掉点，MotherDuck 已证）→ 严格预算 + 召回 | 相对稳健，但同样不喂全量 | 视模型，仍按预算执行 |
| 温度建议 | `0.0 ~ 0.2`（SQL 生成要确定性） | `0.0 ~ 0.2` | `0.0 ~ 0.2` |
| 采样建议 | `top_p=0.9`、关闭重复惩罚 | 同 | 同 |
| 特殊注意 | 少数版本会输出中文解释包裹 SQL → 靠 JSON 契约强约束 | R1 类推理模型可能输出长思维链 → 只取最终 JSON，或用 V3 做生成 | 云 API 有内容审核可能截断 → 需超时/重试兜底 |
| 适配层要求（F-10/N-19） | 切模型不得改前端，仅换配置 | 同 | 同 |

> 共同要求：**温度固定低温**、**max_output_tokens 固定**、**三档模型共享同一套模板与 JSON 契约**，差异只在 system 提示词封装与解析器。

## 7. 版本与变更管理

### 7.1 版本号规则

`模板文件名不变，版本写入文件头`：`版本：vMAJOR.MINOR.PATCH`

| 位 | 触发条件 | 示例 |
|---|---|---|
| MAJOR | 破坏性变更（JSON 契约字段增删/改名、分区顺序变化） | v1.0.0 → v2.0.0 |
| MINOR | 兼容性增强（新增澄清情形、新增 few-shot、调整裁剪阈值） | v1.0.0 → v1.1.0 |
| PATCH | 文案修正、错别字、示例微调 | v1.0.0 → v1.0.1 |

### 7.2 变更流程（门禁）

1. 改模板 → 更新文件头版本号 + 在文件末「变更记录」追加一行（日期/版本/人/内容）。
2. **必跑 Golden SQL 回归集**（`tests/golden/`，20~50 条，见验收 §5）。
3. 门禁：Pass@1 < 70% 或较基线下降 > 5pt → **阻断发布**（验收 §5.5）。
4. 通过后同步更新本文档 §1 与相关变量的说明。

### 7.3 与代码的绑定

- `prompt_version` 须写入每次生成的审计日志（F-26），便于问题回溯到具体模板版本。
- 建议模板以**纯文本文件**存放，随代码仓库版本化（Git），与 `model_profile`、`token_budget` 组成「生成配置快照」。
